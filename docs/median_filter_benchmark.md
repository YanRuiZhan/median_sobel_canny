# 中值滤波性能实验：滑动直方图与插入排序

## 1. 结论

在 `testdata` 的 **4 张完整原图**上，对 `1、3、5、7、9、11、15` 七种核边长进行实验，**没有裁剪、缩放、灰度化或修改输入图片**。每种配置预热一次、正式测量三次，以下耗时均为正式测量的中位数。

- **3×3：滑动直方图快 1.43～1.96 倍**，优势存在，但不是数量级差距。
- **5×5：快 3.58～7.45 倍；9×9：快 10.21～35.70 倍。**
- **15×15：快 26.70～134.52 倍**，核越大，避免逐窗口排序的收益越明显。
- **1×1 是反例**：插入排序更快。直方图仍需扫描灰度桶，而单元素窗口无需排序；不能概括成“直方图在所有核大小下都更快”。
- 84 次正式成对测量的输出全部逐像素一致，包含所有边界和 alpha 通道；另通过 320 组独立正确性测试。

这里比较的是项目当前实现与标准插入排序基线，不是 OpenCV、排序网络或其他专门优化的中值滤波实现。

## 3. 比较对象与实验方法

### 3.1 滑动直方图

直接调用未经修改的 `src/median_blur.cpp` 中的 `icm::median_blur()`：

1. 拆分颜色通道。
2. 每行首个窗口重新建立 256 桶直方图。
3. 沿行向右滑动，减去离开窗口的一列、加上进入窗口的一列。
4. 每个像素从灰度 0 开始累加桶计数，确定中位数。
5. 合并颜色通道，alpha 不参与滤波。

### 3.2 插入排序基线

独立实现位于 [`benchmarks/median_benchmark.cpp`](benchmarks/median_benchmark.cpp)。每个像素重新收集 `k²` 个邻域元素，执行标准原地插入排序，取下标 `k²/2` 的值。

公平性约束：

- 与现有实现一样使用 `Matrix = std::vector<std::vector<int>>`。
- 边界均采用复制填充，图像输出尺寸一致。
- 通道拆分、合并及 alpha 处理逻辑一致。
- 每个通道只分配一次窗口缓冲区，在所有像素间复用，**没有逐像素申请排序缓冲区**。
- 两种实现使用同一编译器和优化选项，不使用线程并行。

**没有直接启用源文件里被注释的 `insertion_sort()`**：其 `j = i - 1` 与后续使用 `arry[j - 1]`、写入 `arry[j]` 的逻辑不匹配，会覆盖错误位置。例如输入 `[1, 9, 5]` 时返回 9，而正确中位数为 5。实验基线使用 `j = i` 的标准写法；原注释代码保持原样。

### 3.3 计时与校验

- 每个“图片×核大小”配置分别完整预热两种算法各一次，预热结果也比较一致性；预热不计入统计。
- 正式测量三轮，调用顺序依次为“直方图→插入”“插入→直方图”“直方图→插入”，减轻固定顺序偏差，但不等价于完全消除顺序影响。
- 计时覆盖完整滤波函数，包括输出内存申请、通道拆分、滤波和合并；不包含图片解码、文件输出、结果比较，也不包含返回结果在计时结束后的销毁。
- 每轮两个完整输出均保留到计时结束后，再逐像素比较；任何不一致立即报错，不输出该轮成功记录。
- 统计量：各算法三轮耗时的中位数。**加速比 = 插入排序耗时中位数 ÷ 直方图耗时中位数**，不是逐轮比值的中位数。
- 完整逐轮记录见 [`benchmarks/median_samples.csv`](benchmarks/median_samples.csv)，共 28 个配置、84 行样本；早期试测数据没有混入正式数据。

## 5. 核大小为何会产生这样的差异

### 5.1 应区分核边长与窗口元素数

令图像高、宽为 `H、W`，核边长为 `k`，桶数为 `B=256`，实际滤波通道数为 `C`。

**逐像素插入排序：**窗口元素数是 `n=k²`，不是 `k`。标准插入排序最坏时间为 `O(n²)=O(k⁴)`；加上采集窗口的 `O(k²)`，整幅图最坏为：

```text
O(C × H × W × k⁴)
```

随机排列下的典型排序工作量也随 `n²` 增长；但图像窗口不是随机排列，常量、重复值、局部有序性会显著减少元素移动。在已排序或全相等的窗口上，排序及窗口收集均为 `O(k²)`，不能把所有实图都视为最坏情况。

**当前滑动直方图：**每个通道每行重建首窗口需要 `O(k²)`，每次横向移动增减两列需要 `O(k)`，寻找中位数最多扫描 `B` 个桶。因此更完整的表达是：

```text
O(C × [H × k² + H × W × (k + B)])
```

在 8 位图像、`B=256` 固定且 `W` 远大于 `k` 时，常简写为 `O(C×H×W×k)`。但这**不是每像素严格 O(1) 的算法**：当前代码没有维护完整的逐列直方图，也没有增量追踪中位数；横向滑动仍需处理 `k` 行。

现有源码和 README 中把“逐像素排序”笼统写成 `O(H×W×k²)`，不适用于这里的插入排序基线；该量级主要对应每像素采集窗口，以及插入排序的最佳情况。本实验只在本文澄清，未修改现有代码或 README。

### 5.2 从 3×3 增长到 15×15

| 图片 | 直方图耗时增长 | 插入排序耗时增长 |
| --- | ---: | ---: |
| Lenna | 1.29× | 86.72× |
| rice | 1.28× | 85.01× |
| house | 1.23× | 84.40× |
| butterfly | 2.66× | 46.68× |

虽然边长增大 5 倍、元素数增大 25 倍，直方图不需要重新排序这 25 倍的元素。小图上，固定的直方图扫描及整图通道处理开销占比较高，因此总耗时仅小幅增加；不能由此推断核大小完全不影响直方图耗时。

Lenna 的 11×11 比 9×9 略快，属于少量重复下的测量波动，不能理解为更大的核有算法优势。

### 5.3 为什么蝴蝶图的加速比没有其他图片高

加速比不仅由尺寸和核大小决定，也与像素分布有关。对原始蝴蝶图作补充统计：

- alpha 为 0 的像素占 **80.6963%**。
- RGB 均为 0 的像素占 **78.778425%**。

当前代码只是保留 alpha，**并不会跳过透明像素的 RGB 滤波**。大量重复值通常会减少插入排序的移动次数；大量低灰度区域也会让直方图更早找到中位数，进而提高列更新等开销的相对占比。这些都是其加速比和增长趋势不同的合理解释，但本实验没有统计每窗口逆序数或逐项剖析 CPU 周期，不能把差异精确归因到其中某一项。

不应直接用不同图片的总毫秒数比较“算法效率”：尺寸、颜色通道数和内容均不同。

### 5.4 1×1 的特殊性

1×1 的正确结果就是输入像素本身。插入排序的排序循环不执行，而当前直方图实现仍逐点找桶，因此插入基线更快。工程上可以对 `k==1` 增加直接返回的快速路径，但本次按要求保留现有代码，**没有加入该优化**。

## 6. 正确性与结果边界

### 已验证

- 所有 84 次完整原图成对测量逐像素一致；预热输出也一致。
- 额外 320 组测试，以 `std::sort` 全排序结果为第三方算法参考，同时检查直方图和插入排序。
- 测试覆盖 1/2/3/4 通道，1×1、1×7、7×1、8×9 图像，0 常量、255 常量、棋盘格、固定种子随机数据，以及 1/3/5/15/31 核；包含核大于图像尺寸的情况。
- AddressSanitizer 和 UndefinedBehaviorSanitizer 下重跑 320 组测试通过。沙箱中的 LeakSanitizer 因 ptrace 限制无法运行，复测设置 `ASAN_OPTIONS=detect_leaks=0`，**未验证内存泄漏**。
- 实验前后对全部 `src/*`、`include/icm/*`、`CMakeLists.txt`、`README.md` 的 SHA-256 校验一致；没有修改、替换或恢复覆盖业务源码，原有实现一直保持原样。

### 限制

- 每配置仅三轮，使用中位数而非置信区间。对 `k≥3` 的配置，三轮极差相对中位数最大约为直方图 **8.27%**、插入排序 **6.35%**；几毫秒的小差异不宜过度解读。
- 未固定 CPU 核心、频率、温度或系统负载；本机还是混合架构 CPU，绝对耗时存在调度及功耗影响。
- 只研究 4 张本地图片和最大 15×15 的完整图像性能；31×31 仅用于小图正确性校验，没有声称测过其完整原图速度。
- 8 位 256 桶假设与当前图片读取流程一致；结论不能直接推广到 16 位或浮点像素。
- 未测量峰值内存、图片读写耗时，未比较优化插入排序变体、排序网络或其他直方图中值算法。

程序每完成一张图的指定核列表，向标准错误输出 `BENCHMARK_PASS`；发生输出不一致时以非零退出。完整蝴蝶图的大核插入排序需要较长时间，请等待运行完成。

正式运行时，终端工具的 shell 收尾曾额外报告 `Cannot set tty process group`。基准程序自身均输出了完成标记，CSV 行数、配置及 PASS 状态也独立核验通过；耗时由程序内部计时器生成，不使用该终端工具的退出状态或墙钟时间。
